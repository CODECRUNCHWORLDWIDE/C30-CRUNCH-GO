# Week 4 — Concurrency II: `context` for Cancellation and Deadlines, the `sync` Primitives, Bounded Worker Pools with `errgroup`, and the Race Detector

Welcome to **C30 · Crunch Go**, Week 4. Last week the wire was channels: we built a fan-out / fan-in pipeline, learned the "who closes the channel" rule, and proved a goroutine leak with a stuck `select`. The question that carried Week 3 was "when is a channel the right synchronisation primitive, and when is it the wrong one." This week the question shifts from *how do goroutines talk to each other* to *how do they stop, how do they share memory safely when a channel is the wrong answer, and how do we prove — not hope — that the result is free of data races.* The technology is the standard library's `context` package, the `sync` and `golang.org/x/sync` primitives, and the Go runtime's race detector (`go test -race`). The standing rule for the week is the same discipline Week 3 demanded of channels, applied to cancellation: **every goroutine you start must have a defined way to stop, and you must be able to point at the line that stops it.**

The first thing to internalize is that **`context.Context` is the cancellation backbone of every Go service**. A `Context` carries three things down a call tree: a cancellation signal (`Done() <-chan struct{}`), an optional deadline (`Deadline() (time.Time, bool)`), and an optional bag of request-scoped values (`Value(key any) any`). You create a root with `context.Background()`, derive children with `context.WithCancel`, `context.WithTimeout`, or `context.WithDeadline`, and you thread the resulting `ctx` as the **first parameter** of every function that does I/O or could block. When the parent is cancelled — the client hung up, the deadline passed, the operator hit Ctrl-C — every descendant `Context` fires its `Done()` channel, and every function blocked on `<-ctx.Done()` or on a `ctx`-aware I/O call unwinds at once. The canonical reference is the package documentation at <https://pkg.go.dev/context> and the Go blog post "Go Concurrency Patterns: Context" at <https://go.dev/blog/context>. Read both this week.

The second thing to internalize is the **cancellation contract**: `context.WithCancel`, `WithTimeout`, and `WithDeadline` each return a `cancel` function, and **you must call it**, normally with `defer cancel()`, even on the success path. The `cancel` function releases the resources the `Context` holds — the timer for a timeout, the child entry in the parent's cancellation tree. Forgetting `defer cancel()` is a *resource leak*, not a logic bug, which is why `go vet` ships a `lostcancel` analyzer that flags it. The deeper point is that cancellation in Go is **cooperative**: calling `cancel()` does not forcibly stop a goroutine, it closes a channel; the goroutine only stops if it is *watching* that channel. A goroutine that runs a tight CPU loop without ever checking `ctx.Err()` or selecting on `ctx.Done()` will run to completion no matter how many times you call `cancel()`. Cancellation is a request, not a kill. Lecture 1 walks the whole `context` tree and the cooperative-cancellation contract end to end.

The third thing to internalize is **when to reach for a `sync` primitive instead of a channel**. Week 3's slogan was "share memory by communicating"; this week is the honest footnote: *sometimes a `sync.Mutex` is simpler, faster, and more obviously correct than a channel.* A mutex protects a small piece of shared state — a counter, a map, a cache — when the access pattern is "lots of goroutines read and write the same in-memory structure." A `sync.RWMutex` is the right tool when reads vastly outnumber writes. `sync.Once` guarantees an initialiser runs exactly once across all goroutines, which is the idiomatic lazy-singleton pattern. `sync.WaitGroup` (Week 3) waits for a known set of goroutines to finish. The rule of thumb, from Bryan Mills' GopherCon talk "Rethinking Classical Concurrency Patterns" at <https://www.youtube.com/watch?v=5zXAHh5tJqQ>: use a channel to *transfer ownership of data or signal an event*; use a mutex to *protect shared state you are not transferring*. Lecture 2 covers all four `sync` types with worked examples and the decision matrix.

The fourth thing to internalize is the **bounded worker pool**. An unbounded fan-out — "spawn one goroutine per item for ten thousand items" — will exhaust file descriptors, open ten thousand sockets at once, and melt the downstream service. A *bounded* pool runs at most N goroutines concurrently regardless of how many items arrive. There are two idiomatic shapes. The first is a **semaphore channel**: a buffered channel of capacity N where every worker sends a token before starting and receives it when done, so the channel's capacity caps concurrency. The second, and the one we standardise on this week, is **`golang.org/x/sync/errgroup`** with `g.SetLimit(n)`: it caps the number of concurrently-running goroutines, collects the first non-nil error, and cancels a derived `Context` when any goroutine fails. `errgroup.WithContext(ctx)` is the single most useful concurrency helper in the Go ecosystem for "run these N things, stop them all if one fails, and give me the first error." Citation: <https://pkg.go.dev/golang.org/x/sync/errgroup>. Lecture 1 and Lab 04 build the pool with `errgroup`.

The fifth thing to internalize is the **data-race model and the memory model**. A data race is *two goroutines accessing the same memory location concurrently, where at least one access is a write, and there is no synchronisation ordering the two*. A data race is not "sometimes wrong" — it is **undefined behaviour**: the program may read a torn value, observe writes out of order, or crash. The Go memory model, specified at <https://go.dev/ref/mem>, defines exactly which operations establish a *happens-before* ordering (a channel send happens-before the corresponding receive; an `Unlock` happens-before the next `Lock`; a `sync/atomic` store happens-before the load that observes it). If you mutate shared state and there is no happens-before edge between the writer and the reader, you have a race, and the only correct fix is to add synchronisation — a mutex, a channel, or an atomic. Lecture 3 walks the memory model at exactly the depth a senior Go interview probes.

The sixth thing to internalize is **what the race detector can and cannot prove**. `go test -race`, `go run -race`, and `go build -race` compile your program with the **ThreadSanitizer** runtime, which instruments every memory access and every synchronisation event, and reports — *at runtime, on the code paths that actually execute* — any pair of accesses that race. The crucial limitation: the race detector finds **only the races that happen on the execution it observes**. A race on a code path your test never exercises is invisible to it. This is why the standing advice is "run your whole test suite under `-race` in CI, and write tests that exercise the concurrent paths." The detector has no false positives — every race it reports is a real race — but it has false negatives for paths you did not run. Citation: the Go blog post "Introducing the Go Race Detector" at <https://go.dev/blog/race-detector> and the data-race-detector reference at <https://go.dev/doc/articles/race_detector>. Lecture 3 reproduces a real race, watches the detector catch it, and fixes it three ways.

The seventh thing to internalize is **`sync/atomic` and when it beats a mutex**. For a single integer counter incremented from many goroutines, a `sync/atomic.Int64` (the Go 1.19+ typed atomic) is both simpler and faster than a `Mutex` guarding an `int64`, because the atomic increment is a single hardware instruction with no lock contention. The typed atomics — `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]` — replace the old free-function `atomic.AddInt64(&x, 1)` style with a struct whose methods cannot be misused (you cannot accidentally read the field non-atomically). The rule: a single scalar accessed concurrently is an atomic; a *group* of fields that must change together is a mutex. Citation: <https://pkg.go.dev/sync/atomic>. Lecture 2 covers the typed atomics and the "atomic vs mutex" decision.

The eighth thing to internalize is **graceful Ctrl-C as `context` cancellation**. The idiomatic way to make a long-running CLI or service respond to Ctrl-C is `signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)`, which returns a `Context` that is cancelled the first time the process receives `SIGINT` or `SIGTERM`. You thread that `ctx` into your worker pool, and the same cancellation machinery that handles a deadline now handles the operator pressing Ctrl-C. This is the seed of the graceful-shutdown story that the whole back half of C30 builds on: *shutdown is just cancellation applied to the top of the call tree.* Citation: <https://pkg.go.dev/os/signal#NotifyContext>. Lab 04 wires `signal.NotifyContext` into the link-checker so that Ctrl-C drains in-flight work cleanly.

The ninth thing to internalize is **benchmarking and a first look at `pprof`**. `go test -bench` runs a function `BenchmarkXxx(b *testing.B)` enough times to get a stable per-operation cost; `b.ReportAllocs()` adds allocation counts; `-benchmem` is the flag. A benchmark sweep across three pool sizes tells you the throughput curve of your worker pool and where adding workers stops helping (because you have saturated the downstream, or the network, or the CPU). `pprof` — reached via `go test -cpuprofile` or the `net/http/pprof` import — turns a slow benchmark into a flame graph that names the function eating the time. We do not go deep on `pprof` this week (that is Week 8), but we take first contact: capture a CPU profile of the worker pool and read the top frame. Citation: the testing package docs at <https://pkg.go.dev/testing#hdr-Benchmarks> and the profiling guide at <https://go.dev/blog/pprof>.

By the end of the week you will be the person on your team who can answer "is this concurrent code correct" with a `-race` run, a benchmark sweep, and a `context` tree you can draw on a whiteboard — not with "it passed on my machine, ship it."

## Learning objectives

By the end of this week, you will be able to:

- **Create and derive** `Context` values with `context.Background()`, `context.WithCancel`, `context.WithTimeout`, and `context.WithDeadline`. Thread `ctx` as the first parameter of every blocking function. Always pair a derived context with `defer cancel()`. Cite <https://pkg.go.dev/context>.
- **Detect** cancellation in a worker with `select { case <-ctx.Done(): return ctx.Err() ... }` and with the `ctx.Err()` check, and explain why cancellation is cooperative — calling `cancel()` closes a channel, it does not kill a goroutine. Cite <https://go.dev/blog/context>.
- **Choose** between a channel and a `sync.Mutex` for a coordination problem, and defend the choice with the "transfer ownership / signal an event → channel; protect shared state → mutex" rule. Cite Bryan Mills' "Rethinking Classical Concurrency Patterns."
- **Protect** shared state with `sync.Mutex` and `sync.RWMutex`, run a one-time initialiser with `sync.Once`, and increment a shared counter with `sync/atomic.Int64`. Justify mutex-vs-atomic in each case. Cite <https://pkg.go.dev/sync> and <https://pkg.go.dev/sync/atomic>.
- **Build** a bounded worker pool with `errgroup.WithContext(ctx)` and `g.SetLimit(n)` that runs at most N goroutines, collects the first error, and cancels its siblings on failure. Cite <https://pkg.go.dev/golang.org/x/sync/errgroup>.
- **Build** the same bound with a semaphore channel (a buffered `chan struct{}` of capacity N) and explain when each shape is preferable. Cite the Go blog "Pipelines and cancellation" at <https://go.dev/blog/pipelines>.
- **Define** a data race precisely (concurrent access, at least one write, no happens-before ordering) and state why it is undefined behaviour, not merely a flaky bug. Cite <https://go.dev/ref/mem>.
- **Find** a data race with `go test -race`, read the ThreadSanitizer report (the two stacks, the "previous write" and "read" lines), and fix it with a mutex, an atomic, or a channel. Explain why the detector has no false positives but does have false negatives for un-exercised paths. Cite <https://go.dev/doc/articles/race_detector>.
- **Wire** graceful Ctrl-C into a CLI with `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` and thread the resulting cancellation into a worker pool. Cite <https://pkg.go.dev/os/signal#NotifyContext>.
- **Write** a `BenchmarkXxx(b *testing.B)` with `b.ReportAllocs()`, run it with `go test -bench . -benchmem`, and read the ns/op and allocs/op columns. Sweep a parameter (pool size) and interpret the throughput curve. Cite <https://pkg.go.dev/testing#hdr-Benchmarks>.
- **Capture** a first CPU profile with `go test -cpuprofile cpu.out -bench .` and read the top frame with `go tool pprof -top cpu.out`. Cite <https://go.dev/blog/pprof>.
- **Cite** the Go standard-library documentation, the Go memory model specification, the `golang.org/x/sync` package docs, and the official Go blog concurrency-patterns series for every technique covered.

## Topics covered

- **The `context` package.** `Background`, `TODO`, `WithCancel`, `WithTimeout`, `WithDeadline`, `WithValue`, the `Done()` channel, `Err()`, the `Deadline()` accessor, the cancellation tree, the `defer cancel()` contract, the `go vet` `lostcancel` check.
- **Cooperative cancellation.** Why `cancel()` closes a channel rather than killing a goroutine; the `select { case <-ctx.Done() }` pattern; the `ctx.Err()` poll; passing `ctx` to `ctx`-aware standard-library calls (`http.NewRequestWithContext`, `db.QueryContext`).
- **Request-scoped values.** `context.WithValue`, the unexported-key-type convention to avoid collisions, why values are for request-scoped metadata (request IDs, auth principals) and *not* for passing optional function parameters.
- **The `sync` primitives.** `sync.Mutex`, `sync.RWMutex`, `sync.Once`, `sync.WaitGroup` (recap), `sync.Pool` (named, not deep), the "do not copy a value containing a `Mutex`" rule that `go vet` enforces.
- **`sync/atomic`.** The typed atomics `atomic.Int64`, `atomic.Uint64`, `atomic.Bool`, `atomic.Pointer[T]`; `Add`, `Load`, `Store`, `Swap`, `CompareAndSwap`; the "atomic for one scalar, mutex for a group" rule.
- **Bounded worker pools.** The semaphore-channel pattern; `errgroup.Group`, `errgroup.WithContext`, `g.Go`, `g.Wait`, `g.SetLimit`; the first-error-wins semantics; cancellation of siblings on failure.
- **The Go memory model.** Happens-before; the synchronisation edges established by channels, mutexes, and atomics; why unsynchronised shared mutation is undefined behaviour.
- **The race detector.** `-race` on `test`, `run`, `build`, `install`; reading a ThreadSanitizer report; no-false-positives / has-false-negatives; the CI discipline of running the suite under `-race`.
- **Graceful Ctrl-C.** `signal.NotifyContext`, `os.Interrupt`, `syscall.SIGTERM`, threading the signal context into a worker pool, the link to graceful shutdown later in the track.
- **Benchmarking.** `testing.B`, `b.N`, `b.ReportAllocs()`, `b.ResetTimer()`, `-bench`, `-benchmem`, `-benchtime`, `-count`; reading ns/op and allocs/op; a parameter sweep across pool sizes; `benchstat` for comparing runs.
- **First contact with `pprof`.** `go test -cpuprofile`, `go tool pprof -top`, the flame-graph idea (deferred to Week 8 for depth).
- **The worked example: a bounded, race-free, cancellable link-checker.** Lab 03's link-checker, converted to a bounded `errgroup` pool with full `context` cancellation (Ctrl-C and `--timeout`), a deliberately-introduced data race that you find with `-race` and fix, and a benchmark sweep across three pool sizes. The numbers are in `mini-project/PERF.md`.

## The "go vet clean" promise — restated, and a new `-race` promise

C30 treats a clean toolchain run as a contract:

```
$ go vet ./... && staticcheck ./... && go test ./...
ok  	github.com/you/linkcheck	0.412s
```

For Week 4 we add a race-detector contract: **every concurrent test you ship in this week's exercises passes under `go test -race`, and you have read at least one ThreadSanitizer report end to end — both stacks, the write line, the read line — and can explain what it caught.** A pull request that adds a goroutine without anyone on the team having run the test suite under `-race` is, by definition, a pull request that has not been reviewed. The detector gives you the report for free; the only requirement is that you pass `-race` and read what it prints.

We add a cancellation contract too: **every goroutine you start in this week's work has a defined way to stop — a `ctx.Done()` it watches, a channel it ranges over until closed, or a `WaitGroup` the parent joins — and you can point at the line that stops it.** The most common concurrency mistake in production Go is a goroutine that nobody can stop. The rule, restated from Week 3's pipeline lecture: a goroutine you cannot stop is a leak waiting to happen.

> **Note on packages.** Everything except `errgroup` is in the standard library: `context`, `sync`, `sync/atomic`, `os/signal`, `testing`. The bounded-pool helper is `golang.org/x/sync/errgroup`, an official `golang.org/x` module (BSD-3-Clause); add it with `go get golang.org/x/sync@latest`. The race detector ships with the Go toolchain; it requires a C compiler on PATH because it is built on ThreadSanitizer. `benchstat` (for comparing benchmark runs) is `golang.org/x/perf/cmd/benchstat`; install it with `go install golang.org/x/perf/cmd/benchstat@latest`. All free, all open source.
