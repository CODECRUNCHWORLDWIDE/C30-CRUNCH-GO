# Week 9 — Observability: Structured Logging with slog, OpenTelemetry Tracing, Prometheus Metrics, and the RED Method

Welcome to **C30 · Crunch Go**, Week 9. Last week made you fluent in the correctness disciplines: table-driven tests, benchmarks that measure the right thing, and fuzzing that finds the inputs you would never have thought to write down. Those tools answer the question "is my code correct in the lab?" This week answers a harder question, the one that arrives at 3am with a pager attached: "my code passed every test, shipped to production, and is now slow — *where*?" The lab cannot answer that. Only the running system can, and only if you instrumented it before the incident. Observability is the discipline of building a service that can be interrogated *after* deployment, by a person who did not write it, under time pressure, with no access to a debugger. By Friday you will be the engineer on your team who can take a latency graph that says "p99 spiked at 14:32" and, in under five minutes, walk it down to the exact line of Go that got slow — because you wired logs, traces, and metrics into the `notes` service so that the three of them point at the same request.

The first thing to internalize is that **there are three signals, and each answers a different question**. **Logs** are the discrete events a service emits — "request started," "validation failed," "row not found." A log line answers *what happened* at a single point in code. **Traces** are the causal tree of a single request as it crosses function, service, and process boundaries — the HTTP handler called the service layer, which called Postgres, which took 412ms. A trace answers *where the time went* for one request. **Metrics** are numeric aggregates over many requests — requests per second, error ratio, the p99 latency over the last five minutes. A metric answers *how the system is behaving in aggregate*, and it is the only one of the three cheap enough to keep for every request at scale. You need all three. A metric tells you *that* the service got slow; a trace tells you *which span* inside one slow request was the culprit; a log line tells you *what that span was doing* when it got slow. Conflate them and you will reach for the wrong tool at 3am.

The second thing to internalize is that **`log/slog` is the standard-library structured logger, and structured beats `fmt` for one concrete reason: machines read logs now, not humans**. A line like `log.Printf("user %s did %s in %dms", id, action, ms)` is a string. To find "every request that took over 500ms," an operator has to write a regex against that string, and the regex breaks the day someone reorders the format. A `slog` line — `logger.Info("request handled", "user_id", id, "action", action, "duration_ms", ms)` — emits a JSON object with typed fields. The query becomes `duration_ms > 500`, evaluated by the log backend, never broken by a format change. `slog` shipped in the standard library in Go 1.21 (citation: <https://go.dev/blog/slog>); it is not a third-party choice you have to defend, it is *the* logger, and the `Handler` interface lets you swap text output in development for JSON in production without touching a single call site.

The third thing to internalize is that **the trace ID is the thread that ties a log line to a span**. This is the single most important idea of the week. When a request arrives, OpenTelemetry assigns it a 16-byte trace ID. Every span in that request's trace carries it. If you also pull that trace ID out of the request context and attach it as an attribute to *every log line* the request emits, then your log backend and your trace backend share a join key. The workflow becomes: the metric dashboard shows a p99 spike; you find one slow request's trace in Jaeger; the trace's slow span has a `trace_id`; you paste that `trace_id` into your log search and read exactly what the code logged while that span was running. Three signals, one identifier, one coherent story. A service whose logs do not carry the trace ID has thrown away the join key and forces the operator to correlate by timestamp and hope — which does not work when you serve ten thousand requests a second.

The fourth thing to internalize is that **OpenTelemetry is vendor-neutral instrumentation plus context propagation, and the propagation is the part people forget**. OpenTelemetry (OTel) is two things: an SDK you call to create spans, and a *propagator* that serializes the current trace context into the outbound request's headers so the next service can continue the same trace. You instrument your code once against the OTel API; you can export to Jaeger today, to a commercial backend tomorrow, with a config change and no code change. But the trace only stays whole if the context propagates: the HTTP server must *extract* the W3C `traceparent` header into the incoming context (the `otelhttp` handler does this), and any outbound call — to another service over gRPC, to Postgres — must run under that context so its spans attach to the same trace. Drop the context at any boundary and the trace breaks into disconnected fragments. Propagation is plumbing, and plumbing that leaks is the most common observability bug there is.

The fifth thing to internalize is the **RED method: for every service, measure Rate, Errors, and Duration**. This is the opinionated answer to "which metrics should I emit?" — and the answer that has survived a decade of production use (citation: Tom Wilkie's RED method, <https://www.weave.works/blog/the-red-method-key-metrics-for-microservices-architecture/>). **Rate** is requests per second, the `rate()` of a counter. **Errors** is the rate of failed requests, the ratio of a filtered counter to the total. **Duration** is the latency distribution, computed from a *histogram* — and it must be a histogram, not an average, because the average hides the tail and the tail is what pages you. Three signals per endpoint, computed in PromQL from two Prometheus instruments: an `http_requests_total` counter labeled by method/route/code, and an `http_request_duration_seconds` histogram labeled by method/route. Get those two right, with disciplined labels, and you can build a dashboard that tells you the health of every endpoint at a glance.

The sixth thing to internalize is that **a dashboard localizes and a trace pinpoints — they are not the same tool, and using one for the other's job wastes the incident**. A Grafana dashboard built over RED metrics shows you, in aggregate, *that* the `GET /notes/{id}` route's p99 doubled at 14:32. It cannot tell you *why* — metrics are aggregates, they have no per-request detail by design (a metric labeled by note ID would explode your cardinality and bankrupt your metrics backend; more on that in Lecture 3). The dashboard's job is to *localize*: which route, which time, which signal moved. Then you switch tools. You open a slow trace for that route in Jaeger and read the span tree, and the trace *pinpoints*: the `db.query` span took 380ms of the 400ms request. The dashboard narrowed the search space from "the whole service" to "this route at this time"; the trace narrowed it from "this route" to "this line." That two-step — localize on the dashboard, pinpoint in the trace — is the muscle this week builds, and the mini-project drills it directly by injecting an artificial slow query and making you find it.

The final thing to internalize is that **observability is the operational contract a service owes its operators**. Tests are the contract you owe other developers; observability is the contract you owe whoever is on call. A service that emits structured, trace-correlated logs, that puts every handler under a span exported to a trace backend, and that exposes RED metrics behind a dashboard, is a service that a stranger can debug at 3am without waking you. A service that logs unstructured strings, has no traces, and exposes a single "uptime" gauge is a service that *only you* can debug, slowly, by SSHing in and reading. The first is a professional artifact; the second is a liability with your name on it. This week you upgrade `notes` from the second kind to the first.

## Learning objectives

By the end of this week, you will be able to:

- **Emit** structured logs with `log/slog`: choose between `slog.NewTextHandler` and `slog.NewJSONHandler`, set levels with `slog.HandlerOptions` and change them at runtime with a `slog.LevelVar`, and attach typed attributes with `slog.String`/`slog.Int`/`slog.Any`/`slog.Group` rather than formatting strings.
- **Build** a request-scoped logger: use `slog.With` to bind `request_id` and `trace_id` once per request, stash the bound logger in the request `context.Context`, and retrieve it in every layer so every log line for a request shares the same fields.
- **Write** a custom `slog.Handler` (or a middleware) that pulls the current trace ID out of the context and injects it as a `trace_id` attribute on every record, so logs and traces share a join key.
- **Set** the process-wide default logger with `slog.SetDefault`, and explain when reaching for the default is acceptable versus when an injected, request-scoped logger is mandatory.
- **Initialize** the OpenTelemetry SDK: build a `resource` with the `semconv` `service.name`, construct a `TracerProvider` with a `BatchSpanProcessor` and an OTLP exporter, register it with `otel.SetTracerProvider`, and set `otel.SetTextMapPropagator(propagation.TraceContext{})`.
- **Create** spans correctly: `tracer.Start(ctx, "name")`, defer `span.End()`, add `span.SetAttributes`, record failures with `span.RecordError` and `span.SetStatus(codes.Error, ...)`, and pass the returned context down so child spans attach to the parent.
- **Propagate** trace context across boundaries: wrap the HTTP entry point with `otelhttp.NewHandler` so the W3C `traceparent` header is extracted, and use the `otelgrpc` stats handler on both gRPC client and server so a trace spans two services.
- **Instrument** the handler → service → Postgres path with a span per layer, including the database span (via `otelpgx` or a manual span), so the trace shows where the time went inside one request.
- **Shut down** the `TracerProvider` cleanly: call `Shutdown(ctx)` on process exit so the `BatchSpanProcessor` flushes buffered spans instead of dropping them.
- **Expose** Prometheus metrics with `client_golang`: register a `CounterVec` and a `HistogramVec` on a `prometheus.Registry`, serve them with `promhttp.HandlerFor` at `/metrics`, and choose histogram buckets deliberately (`prometheus.DefBuckets` or explicit exponential buckets for latency).
- **Implement** the RED method as middleware: `http_requests_total{method,route,code}` and `http_request_duration_seconds{method,route}`, with strict cardinality discipline — never a label whose value is unbounded, like a note ID.
- **Query** the metrics in PromQL — `rate()` for rate, a filtered-counter ratio for errors, `histogram_quantile()` for p95/p99 — and read each one off a Grafana panel.
- **Localize** a latency regression: read a p99 spike off the Grafana RED dashboard, identify the slow route, open a slow trace for that route in Jaeger, and pinpoint the span that consumed the time.

## Topics covered

- **`log/slog` fundamentals.** `slog.Logger`, the `slog.Handler` interface (`Enabled`, `Handle`, `WithAttrs`, `WithGroup`), `slog.NewTextHandler` vs `slog.NewJSONHandler`, `slog.HandlerOptions` (`Level`, `AddSource`, `ReplaceAttr`), the four levels (`Debug`/`Info`/`Warn`/`Error`), `slog.LevelVar` for runtime level changes.
- **Structured attributes.** `slog.String`/`Int`/`Int64`/`Bool`/`Time`/`Duration`/`Any`, `slog.Group` for nesting, the `slog.Attr` vs `...any` performance distinction, and the `slog.LogValuer` interface for lazy and redacting attributes.
- **Request-scoped logging.** `slog.With` to bind per-request fields, stashing a `*slog.Logger` in `context.Context`, `slog.InfoContext` and context-aware handlers, `slog.SetDefault` and when it is appropriate.
- **Log/trace correlation.** Extracting the trace ID from `trace.SpanContextFromContext(ctx)`, attaching it as a `trace_id` log attribute, and the join-key workflow across log and trace backends.
- **The OpenTelemetry data model.** Trace, span, span context, trace ID / span ID, attributes, events, status; parent/child relationships; the W3C `traceparent` header.
- **OTel SDK setup.** `resource.New` with `semconv.ServiceName`, `sdktrace.NewTracerProvider` with a `BatchSpanProcessor`, the OTLP exporter (`otlptracegrpc` / `otlptracehttp`) to a local Jaeger, `otel.SetTracerProvider`, `otel.SetTextMapPropagator(propagation.TraceContext{})`, and `TracerProvider.Shutdown` to flush.
- **Span creation.** `otel.Tracer(name).Start(ctx, "span")`, `span.End()`, `span.SetAttributes(attribute.String(...))`, `span.AddEvent`, `span.RecordError(err)`, `span.SetStatus(codes.Error, msg)`.
- **Context propagation.** `otelhttp.NewHandler` on the HTTP boundary, the `otelgrpc` stats handler on gRPC, why a dropped context breaks the trace, and instrumenting handler → service → Postgres with one span per layer.
- **Prometheus `client_golang`.** The registry (`prometheus.NewRegistry`, `DefaultRegisterer`), the metric types (`Counter`, `Gauge`, `Histogram`, `Summary`) and when each fits, `CounterVec`/`HistogramVec` with labels, `prometheus.DefBuckets` and exponential buckets, `promauto`, `promhttp.HandlerFor` exposing `/metrics`.
- **The RED method.** Rate/Errors/Duration as middleware, the counter+histogram pair, cardinality discipline, the gRPC equivalent.
- **PromQL and Grafana.** `rate()`, `histogram_quantile()` for p95/p99, the error ratio, building a Grafana panel per RED signal, provisioning a dashboard from JSON, and the full local stack via `docker compose`.
- **Localizing a regression.** Dashboard p99 spike → slow route → open the trace → the slow DB span. The artificial-slow-query drill.

## The observability contract — restated

Weeks 5–8 treated a green test run as the contract you owe other developers:

```
ok  	github.com/crunch/notes/internal/service	0.412s
```

For Week 9 we add the contract you owe whoever is on call. By Sunday, the `notes` service obeys four rules, and the mini-project rubric checks each one:

- **Every request emits a trace-correlated log line.** Request start and request end are logged through a request-scoped `slog.Logger` that carries `request_id` and the live `trace_id`. An operator who finds a slow trace in Jaeger can paste its `trace_id` into the log search and read exactly what the code was doing.
- **Every handler is a span.** The HTTP entry point is wrapped with `otelhttp`, the service layer opens a child span, and the Postgres call opens its own span. One request is one connected trace from the front door to the database, exported to a local Jaeger you can read in a browser.
- **Every endpoint exports RED metrics.** A counter and a histogram, labeled by method and route, give you rate, error ratio, and the latency distribution in PromQL — with cardinality discipline so the metrics backend never sees an unbounded label.
- **A dashboard plus a trace can localize any latency regression.** When you inject an artificial slow query, the Grafana RED dashboard shows the p99 spike on the affected route within one scrape interval, and the trace for that route pinpoints the slow span. The dashboard localizes; the trace pinpoints. If you cannot walk that path in five minutes, the instrumentation is incomplete — fix it before you call the lab done.

A service that ignores its observability contract is the operational equivalent of a function with no tests: it works right up until it does not, and when it does not, nobody can tell you why. We do not ship those.
