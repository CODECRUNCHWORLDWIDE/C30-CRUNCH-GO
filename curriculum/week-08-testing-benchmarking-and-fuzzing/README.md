# Week 8 — Testing, Benchmarking and Fuzzing in Go: Table-Driven Tests, Test Doubles, Integration Tests, `testing.B`, `pprof`, and `go test -fuzz`

Welcome to **C30 · Crunch Go**, Week 8. The last three weeks made you fluent in the *shape* of a service: a `net/http` + `chi` REST API with a handler/service/repository split (Week 5), a Postgres data layer with `pgx`, `sqlc`, and `golang-migrate` (Week 6), and a gRPC surface with protobuf and `buf` (Week 7). You can build the thing. This week answers a harder question: *how do you know it works, and how do you know it is fast enough?* The answer is not "I ran it once and it looked fine." The answer is a layered test suite that runs in milliseconds for the common case, an integration suite that runs against a real Postgres when it earns its slowness, a benchmark that measures the hot path instead of guessing at it, a `pprof` profile that points at the actual bottleneck, and a fuzz target that finds the malformed input you would never have thought to type by hand. By Sunday you will be the person on your team who can look at a pull request and say, with evidence, "this is tested, this is measured, and the parser does not panic on garbage."

The first thing to internalize is **the testing pyramid for a Go service**. The base is unit tests: fast, in-memory, no I/O, thousands of them, running in under a second on `go test ./...`. The middle is integration tests: a real Postgres in a container, real SQL, real migrations, dozens of them, running in tens of seconds and gated behind a build tag so they do not slow your inner loop. The thin top is end-to-end tests: the whole service up, a real HTTP client hitting real endpoints, a handful of them, run in CI. The pyramid is a shape, not a rule, but the shape encodes a truth: the cheaper a test is to run, the more of them you can afford, and the faster your feedback loop gets. A suite that is all integration tests is a suite nobody runs locally because it takes four minutes; a suite that is all unit tests with mocked databases is a suite that passes while production is on fire because the SQL was wrong. You want both, in the right proportion.

The second thing to internalize is that **table-driven tests are the Go idiom, not a style preference**. Go has no `[Theory]` attribute, no parameterized-test framework, no `describe`/`it` DSL. What it has is a slice of structs and a `for` loop, and that turns out to be enough — more than enough. You declare a `[]struct{ name string; in T; want U }`, you range over it, you call `t.Run(tc.name, func(t *testing.T) { ... })` for each case, and you get named subtests that run independently, report independently, and can run in parallel with `t.Parallel()`. Adding a case is one line. The whole pattern is in the standard library's own test suite, in the Go team's "Prefer table driven tests" doctrine (Dave Cheney, <https://dave.cheney.net/2019/05/07/prefer-table-driven-tests>), and in the official wiki at <https://go.dev/wiki/TableDrivenTests>. Lecture 1 makes you fluent in it.

The third thing to internalize is that **test doubles in Go are small interfaces, not a mocking framework**. Your Week 5 service depended on a `Repository` interface — a handful of methods. To test the service without a database, you do not reach for `gomock` or `testify/mock`; you write a struct that implements `Repository` with in-memory maps and canned errors, twenty lines, and you inject it. This is the "accept interfaces, return structs" proverb cashing out at test time. The interface is defined *by the consumer* (the service), it is *small* (only the methods the service uses), and the fake is *obvious* (you can read it and see exactly what it returns). A generated mock with `EXPECT().Foo().Return(...).Times(1)` is harder to read, couples your test to call order you did not mean to assert, and hides the behaviour you are faking behind a DSL. Lecture 1 builds the fake by hand and explains when — rarely — a mock is the better tool.

The fourth thing to internalize is that **integration tests earn their slowness, and you make that bargain explicit with a build tag**. A unit test that fakes the repository proves your *logic* is right; it cannot prove your *SQL* is right, because there is no SQL. For that you need a real Postgres. `testcontainers-go` brings one up in a Docker container, gives you a connection string, runs your migrations, and tears it down when the test ends — all from inside `go test`. It is slow (a container start is seconds, not microseconds), so you put it behind `//go:build integration` and run it with `go test -tags=integration`. Your inner loop stays fast; your CI runs the real thing. When Docker is absent, the test `t.Skip`s instead of failing. Lecture 3 covers the whole pattern, including parallel-safe isolation so two integration tests do not stomp each other's rows.

The fifth thing to internalize is that **benchmarks measure, and `testing.B` plus `benchstat` are how you measure honestly**. A benchmark is a function `func BenchmarkX(b *testing.B)` with a `for range b.N` loop; the framework runs the loop enough times to get a stable timing and reports `ns/op`. Add `b.ReportAllocs()` and you also get `B/op` and `allocs/op` — the allocation count is often the number that matters, because allocations create garbage and garbage creates GC pressure. The two traps are everywhere: the compiler will delete your benchmark body if its result is unused (assign to a package-level *sink* to defeat dead-code elimination), and a single run tells you nothing about variance (run with `-count=10` and feed two runs to `benchstat`, which computes a p-value and tells you whether the difference is real or noise). Lecture 2 walks a complete A/B: benchmark a slow path, see the allocations, fix them, re-benchmark, and read the `benchstat` delta.

The sixth thing to internalize is that **`pprof` finds the hot path so you optimize the right thing**. Your intuition about where a program spends its time is wrong more often than it is right. `pprof` replaces the intuition with a measurement. `go test -cpuprofile=cpu.out -bench=.` records where the CPU went; `go tool pprof cpu.out` lets you list the hot functions (`top`), annotate a function line-by-line (`list`), and render a flame graph in the browser (`web`). There are five profile types and each answers a different question: CPU for "what is burning cycles," heap for "what is allocating," goroutine for "is something leaking goroutines," block for "what is waiting on channels and locks," mutex for "what is contended." Lecture 2 reads a real flame graph and ships one measured optimization.

The seventh thing to internalize is that **fuzzing finds the inputs you did not think of**. You write table-driven tests for the cases you imagined. The fuzzer writes the cases you did not: the empty string, the string that is all delimiters, the input that is one byte short of a header, the UTF-8 that is almost-but-not-quite valid. Native Go fuzzing (GA since Go 1.18, <https://go.dev/doc/go1.18#fuzzing>) is `func FuzzX(f *testing.F)` with `f.Add(seed)` corpus entries and `f.Fuzz(func(t *testing.T, in string) { ... })`. Inside the fuzz function you assert an *invariant* — never panics, parse-then-serialize round-trips, the output is always valid — and the engine mutates inputs looking for one that breaks the invariant. When it finds one it writes the crashing input to `testdata/fuzz/` so the bug becomes a permanent regression test. Lecture 3 runs a fuzz target that finds a real index-out-of-range and fixes it.

The eighth thing to internalize is that **coverage is a signal, not a goal**. `go test -cover` tells you what fraction of statements ran during the test. That number is useful as a *floor finder* — a package at 12% coverage has untested code and you should be suspicious — and useless as a *target*, because 100% coverage is trivially gameable (call every line once, assert nothing) and chasing it produces tests that assert the implementation rather than the behaviour. A well-tested package is usually somewhere in the 70–90% range, with the gaps being error paths that are genuinely hard to trigger and getters that are not worth a test. Read coverage to find the *holes you forgot*, not to hit a number a dashboard demands. Lecture 1 covers `go tool cover -html` and why 100% is a smell.

## Learning objectives

By the end of this week, you will be able to:

- **Write** table-driven tests at scale: a `[]struct{ name string; ... }` table, a `for` loop with `t.Run(tc.name, ...)` subtests, `t.Parallel()` for independent cases, `t.Helper()` on assertion helpers, and `t.Cleanup()` for teardown. Cite the `testing` godoc and the table-driven-tests wiki.
- **Assert** without a framework: use `==` and `reflect.DeepEqual` for simple values, and `github.com/google/go-cmp/cmp` with `cmpopts` for structs, unexported fields, and floating-point tolerance — and explain why `cmp.Diff` beats `reflect.DeepEqual` for test output.
- **Author** golden-file tests: a `testdata/` directory, an `-update` flag that rewrites the golden file with `os.WriteFile`, a normal run that compares against it with `os.ReadFile`, and the workflow for reviewing a golden diff in code review.
- **Build** test doubles as small consumer interfaces: a hand-written fake implementing the Week-5 `Repository` interface with in-memory state and injectable errors, injected into the service under test — no mocking library.
- **Test** HTTP handlers with `net/http/httptest`: `httptest.NewRecorder` for a single handler, `httptest.NewServer` for a full round-trip, and assertions on status, headers, and body.
- **Write** a benchmark with `testing.B`: the `b.N` loop, `b.ResetTimer`, `b.ReportAllocs`, `b.Run` sub-benchmarks, and `b.RunParallel`/`pb.Next` for concurrent paths — and defeat dead-code elimination with a package-level sink.
- **Compare** two implementations with `benchstat`: run each with `-count=10`, feed both result files to `benchstat`, and read the percentage delta and the p-value to decide whether a change is a real improvement or noise.
- **Capture** a `pprof` profile from a benchmark (`-cpuprofile`, `-memprofile`) or a running service (`net/http/pprof`), and read it with `go tool pprof` — `top`, `list`, `web` — including a flame graph.
- **Choose** the right profile for the symptom: CPU for a spinning hot loop, heap for excess allocation, goroutine for a leak, block for channel/lock waits, mutex for lock contention; and enable the last two with `runtime.SetBlockProfileRate` / `runtime.SetMutexProfileFraction`.
- **Write** a fuzz target with `testing.F`: `f.Add` seed corpus, `f.Fuzz` with a typed input and an invariant assertion (never-panic, round-trip, output-validity), run it with `go test -fuzz=FuzzX -fuzztime=30s`, and interpret the crasher the engine writes to `testdata/fuzz/`.
- **Stand up** an integration test against a real Postgres with `testcontainers-go`: bring up the `postgres` module, run migrations in `TestMain`, gate the suite behind `//go:build integration`, `t.Skip` when Docker is absent, and isolate parallel tests so they do not collide.
- **Read** a coverage report as a signal: `go test -coverprofile`, `go tool cover -html`, and the judgment to find the holes that matter without chasing 100%.

## Prerequisites

- **Weeks 5–7 of C30 complete.** You have a `notes` service with a handler/service/repository split, a Postgres data layer with `pgx`/`sqlc`/`golang-migrate`, and you can read and write Go interfaces. This week hardens exactly that service.
- **Go 1.22 or later.** `go version` should report `go1.22.x` or newer. We rely on generics, `log/slog`, and the post-1.22 loop-variable semantics (each iteration gets a fresh `i` and value — the old `t.Parallel()` capture footgun is gone, and we explain why). Native fuzzing has been GA since 1.18; everything we use is stable.
- **Docker installed and running** for the integration tests and the `testcontainers-go` work. `docker info` should succeed without `sudo` (or you have rootless Docker configured). On macOS, Docker Desktop or Colima both work. If Docker is absent, the integration tests `t.Skip` and the rest of the week runs unaffected.
- **`benchstat`** installed as a tool: `go install golang.org/x/perf/cmd/benchstat@latest`. It compares benchmark runs and computes statistical significance. Free, first-party, two-second install.
- **`graphviz`** is optional but recommended for `go tool pprof -web` (the flame-graph/dot rendering). `brew install graphviz` on macOS. Without it, `top` and `list` still work; only the graphical `web` view needs it.

## Topics covered

- **The `testing` package.** `func TestX(t *testing.T)`, `t.Error`/`t.Errorf` vs `t.Fatal`/`t.Fatalf`, `t.Run` subtests, `t.Parallel`, `t.Helper`, `t.Cleanup`, `t.TempDir`, the `testing.TB` interface, `TestMain` for suite-level setup and teardown, the `-run`/`-v`/`-count`/`-race`/`-short` flags.
- **Table-driven tests.** The `[]struct{ name string; in...; want...; wantErr bool }` table, the range-and-`t.Run` loop, naming cases for readable failure output, `t.Parallel()` inside the subtest, and the post-Go-1.22 loop-variable semantics.
- **Assertions without a framework.** `==`, `reflect.DeepEqual`, and `github.com/google/go-cmp/cmp` with `cmp.Diff`, `cmpopts.IgnoreFields`, `cmpopts.EquateApprox`, and `cmp.AllowUnexported`. Why a diff beats a boolean.
- **Golden-file tests.** `testdata/` (the directory `go test` ignores for compilation), the `var update = flag.Bool("update", ...)` pattern, `os.WriteFile`/`os.ReadFile`, and the code-review workflow for golden diffs.
- **Test doubles.** Consumer-defined small interfaces, hand-written fakes with in-memory state, injectable errors via fields, stubs vs fakes vs mocks, and when (rarely) a generated mock earns its keep.
- **HTTP testing.** `httptest.NewRecorder`, `httptest.NewServer`, `http.Handler` testing, the `chi` router under test, asserting on status/headers/body.
- **Benchmarks.** `func BenchmarkX(b *testing.B)`, the `b.N` loop, `b.ResetTimer`, `b.StopTimer`/`b.StartTimer`, `b.ReportAllocs`, `b.SetBytes`, `b.Run` sub-benchmarks, `b.RunParallel` + `pb.Next`, the dead-code-elimination sink, and `go test -bench=. -benchmem -count=10`.
- **`benchstat`.** Running with `-count=N`, capturing old/new result files, the percentage delta, the `±` geomean, and the p-value as a significance gate.
- **`pprof`.** `runtime/pprof` and `net/http/pprof`, `go test -cpuprofile/-memprofile/-blockprofile/-mutexprofile`, `go tool pprof`, `top`/`list`/`web`/`peek`, flame graphs, the five profile types and the symptom each diagnoses, `runtime.SetBlockProfileRate` and `runtime.SetMutexProfileFraction`.
- **Fuzzing.** `func FuzzX(f *testing.F)`, `f.Add` seed corpus, `f.Fuzz` with typed inputs, the invariant mindset (never-panic, round-trip, output-validity), `go test -fuzz=FuzzX -fuzztime=30s`, the seed corpus in `testdata/fuzz/`, and the crasher entry the engine writes on failure.
- **Integration tests.** `//go:build integration` build tags, `testcontainers-go` and the `postgres` module, `wait.ForListeningPort`/`wait.ForSQL`, running migrations in `TestMain`, the compose-harness alternative, `t.Skip` when Docker is absent, and schema-per-test / transaction-rollback isolation.
- **Coverage.** `go test -cover`, `-coverprofile`, `go tool cover -func`, `go tool cover -html`, coverage as a hole-finder, and why 100% is a smell.

## The test contract — restated

C30 treats `go build ./...` and `go vet ./...` as the floor, not the ceiling. For Week 8 we add a test contract that every change you ship must honour:

- **Every change ships with a table-driven test.** A bug fix ships with the failing case added to the table. A feature ships with its happy path and its error paths in the table. "I tested it manually" is not a test; a `_test.go` file is.
- **The hot path has a benchmark.** If you claim a function is fast, there is a `BenchmarkX` proving it, and if you optimize it, there is a `benchstat` delta proving the optimization is real and not noise.
- **Input parsing has a fuzz target.** Any code that turns untrusted bytes — an HTTP body, a query string, a header, a file — into a structured value has a `FuzzX` asserting it never panics and, where it applies, round-trips. The fuzzer finds the input you did not type.
- **It is clean under `go vet ./...` and `go test -race ./...`.** `go vet` catches the mechanical mistakes (a `Printf` with the wrong verb, a lock copied by value); the race detector catches the data races your tests would otherwise pass through silently. Both are non-negotiable before a PR.

> **Note on Docker.** Some learners will run this week's integration tests on a machine without Docker, or in a CI image that lacks a Docker daemon. The integration tests are written to `t.Skip` cleanly in that case — they will not fail your `go test ./...`, they will simply not run. Installing Docker is your responsibility for the parts that need it: <https://docs.docker.com/get-docker/> is free and the desktop installer takes a few minutes. On macOS, Colima (`brew install colima && colima start`) is a lighter free alternative that `testcontainers-go` drives identically. The unit tests, the benchmarks, the `pprof` work, and the fuzzing all run with no Docker at all.
