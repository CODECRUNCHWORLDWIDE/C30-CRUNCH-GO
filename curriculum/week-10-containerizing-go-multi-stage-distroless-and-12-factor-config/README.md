# Week 10 — Containerizing Go: Multi-Stage, Distroless, and 12-Factor Config — Turning the `notes` Service into a Small, Static, Non-Root Image That Reads Every Setting From the Environment

Welcome to **C30 · Crunch Go**, Week 10 — the first week of Phase III, where the service you have been building since Week 5 stops being "a program that runs on my laptop" and becomes "an artifact that runs anywhere." Week 9 made `notes` observable: `slog` structured logs correlated with trace IDs, OpenTelemetry traces exported to Jaeger across the HTTP handler → service → Postgres path, and Prometheus RED metrics behind a Grafana dashboard. The service emits everything an operator needs at 3 AM. This week we package it. The same `notes` service — `cmd/notesd`, the `chi` REST surface from Week 5, the gRPC server from Week 7, the `pgx`+`sqlc` data layer from Week 6, the instrumentation from Week 9 — goes into a **multi-stage, distroless, non-root container image**, gets configured **entirely through the environment** (12-factor), and comes up as part of a one-command local stack alongside Postgres, Jaeger, Prometheus, and Grafana. We do not invent a new project. We ship the one we built.

The first thing to internalize is that **a Go container should be small, static, non-root, and start in milliseconds — and the language makes all four nearly free**. Go compiles to a single static binary with no runtime to install, no interpreter, no shared-library tree to drag along. With `CGO_ENABLED=0` the binary depends on *nothing* at runtime, which is why a Go service can ship on `scratch` (literally an empty image) or on a distroless base that carries only CA certificates and timezone data. A naive `golang:1.22` image ships the entire toolchain — the compiler, the standard library source, `git`, a shell — three-quarters of a gigabyte of attack surface that never runs in production. A multi-stage build separates the *build* stage (`golang:1.22`) from the *runtime* stage (`gcr.io/distroless/static-debian12` or `scratch`), copying only the compiled binary forward. The result is an image measured in single-digit to low-double-digit megabytes. The canonical reference is the Docker multi-stage-build guide at <https://docs.docker.com/build/building/multi-stage/> and the Google distroless repository at <https://github.com/GoogleContainerTools/distroless>.

The second thing to internalize is that **config is environment, not code, and not a baked-in file**. The Twelve-Factor App's factor III is blunt: strict separation of config from code, with config read from the environment. A database password compiled into the binary or copied into an image layer is a credential you cannot rotate without a rebuild and a leak waiting to be `docker history`'d out. A service configured from the environment is the *same image* in dev, staging, and production — only the `DATABASE_URL`, the `OTEL_EXPORTER_OTLP_ENDPOINT`, and the `LOG_LEVEL` change. This week we move every setting `notes` has into an env-driven config struct loaded once at startup, validated, and never read from again. The reference is <https://12factor.net/config> and, for the broader checklist, <https://12factor.net/>.

The third thing to internalize is that **the runtime image is part of your threat surface, and distroless is the cheapest way to shrink it**. A `debian`- or `alpine`-based runtime ships a shell, a package manager, `curl`, `wget`, and a userland an attacker uses to live off the land after a compromise. Distroless ships none of that — no shell, no `sh`, no busybox, no apt — only your binary, CA certs, `/etc/passwd` with a `nonroot` user, and tzdata. There is nothing to `exec` into, nothing to pivot through. The tradeoff is that `kubectl exec -it ... -- sh` does not work (there is no shell), which is a feature in production and a mild inconvenience you pay back with the logs and traces you built in Week 9. The reference is the distroless `static` image docs at <https://github.com/GoogleContainerTools/distroless/blob/main/base/README.md>.

The fourth thing to internalize is that **non-root is not optional, and it is one line**. A container that runs as UID 0 is a container escape away from root on the node. The distroless images ship a `nonroot` user (UID 65532); the `USER nonroot:nonroot` (or `USER 65532:65532`) line in the Dockerfile, plus a binary that binds a high port (8080, not 80, which a non-root process cannot bind), is the whole story. We set it, and we prove it with `docker run ... id` — except distroless has no `id` either, so we prove it with the Kubernetes `securityContext` in Week 11 and with the image's `/etc/passwd`. The reference is the Docker `USER` instruction docs at <https://docs.docker.com/reference/dockerfile/#user> and the Kubernetes pod-security-standards doc at <https://kubernetes.io/docs/concepts/security/pod-security-standards/>.

The fifth thing to internalize is that **build order is performance, and the Go build cache is the lever**. Copying `go.mod` and `go.sum` and running `go mod download` *before* copying the source means the module-download layer is cached and only re-runs when a dependency changes — not on every source edit. With BuildKit cache mounts (`--mount=type=cache,target=/go/pkg/mod` and `target=/root/.cache/go-build`), even the compile cache persists across builds. The difference between a 5-second and a 60-second rebuild is one correctly-ordered `COPY`. The reference is the Docker build-cache doc at <https://docs.docker.com/build/cache/> and the cache-mount reference at <https://docs.docker.com/build/cache/optimize/>.

The sixth thing to internalize is that **logs go to stdout, the process is stateless, and it shuts down cleanly — the 12-factor disposability factors that Kubernetes will lean on next week**. A 12-factor process writes its event stream to stdout and lets the platform route it (factor XI); holds no state on local disk that it cannot lose (factor VI); and starts fast and shuts down gracefully on `SIGTERM` (factor IX). Week 9's `slog` already writes JSON to stdout. This week we make the process stateless (all state is in Postgres) and confirm it. Next week (Week 11) we make the graceful-shutdown half rigorous under Kubernetes; this week we lay the 12-factor groundwork the cluster will assume. The reference is <https://12factor.net/logs>, <https://12factor.net/processes>, and <https://12factor.net/disposability>.

The seventh thing to internalize is that **the full stack composes locally, one `docker compose up` away from the cloud topology**. The capstone deploys `notes` to Kubernetes against Postgres, Jaeger, Prometheus, and Grafana. Before you trust the cluster, you prove the image composes with its dependencies on your laptop: a `compose.yaml` brings up the service, Postgres, Jaeger, Prometheus, and Grafana together, wired by environment variables, so the same image you will ship to `kind` next week runs against the same dependency shape it will meet there. The reference is the Compose specification at <https://docs.docker.com/compose/> and the `depends_on` healthcheck reference at <https://docs.docker.com/reference/compose-file/services/#depends_on>.

By the end of this week you will be the engineer who can take a Go service from `go build` to a sub-15-MB distroless image that runs as a non-root user, reads every setting from the environment, logs JSON to stdout, and brings its whole observability stack up with one command — the artifact Week 11 deploys to Kubernetes and the capstone defends. That is the difference between someone who writes Go services and someone who *ships* them.

## Learning objectives

By the end of this week, you will be able to:

- **Author** a multi-stage Dockerfile for `notesd` that builds a static `CGO_ENABLED=0` binary in a `golang:1.22` stage and ships it on `gcr.io/distroless/static-debian12` as a non-root user, producing an image you can `docker run` locally. Cite <https://docs.docker.com/build/building/multi-stage/>.
- **Explain** why `CGO_ENABLED=0` matters for distroless and `scratch`, and what breaks (DNS resolution edge cases, `os/user`) if you ship a CGO-linked binary on an image with no libc. Cite <https://pkg.go.dev/cmd/cgo> and the distroless static README at <https://github.com/GoogleContainerTools/distroless/blob/main/base/README.md>.
- **Order** the Dockerfile so `go.mod`/`go.sum` copy and `go mod download` precede the source copy, and add BuildKit cache mounts so the module and build caches persist across rebuilds. Cite <https://docs.docker.com/build/cache/>.
- **Configure** `notes` entirely through the environment with a validated config struct loaded once at startup, and reason about why a baked-in secret is a rotation and leak hazard. Cite <https://12factor.net/config>.
- **Write** a `.dockerignore` that keeps the Git tree, local env files, test caches, and the compose stack out of the build context. Cite <https://docs.docker.com/build/concepts/context/#dockerignore-files>.
- **Run** the image as a non-root user and confirm it (the `nonroot` UID 65532, a high port, no shell to exec into), and state what distroless gives, costs, and forbids. Cite the distroless base README at <https://github.com/GoogleContainerTools/distroless/blob/main/base/README.md>.
- **Compose** the full local stack — `notesd` + Postgres + Jaeger + Prometheus + Grafana — with `docker compose up`, wired by environment variables and gated by Postgres's healthcheck. Cite <https://docs.docker.com/compose/>.
- **Measure** the final image size across single-stage, multi-stage `debian`, multi-stage distroless, and `scratch`, and explain every number. Cite the distroless repo at <https://github.com/GoogleContainerTools/distroless>.
- **Apply** the 12-factor disposability factors — logs to stdout, stateless process, fast startup — and identify which Week 11 work (graceful shutdown) completes the disposability story. Cite <https://12factor.net/disposability> and <https://12factor.net/logs>.
- **Cite** docs.docker.com (multi-stage, build cache, Compose, `.dockerignore`), the GoogleContainerTools/distroless repository, 12factor.net (config, logs, processes, disposability), and pkg.go.dev for each technique covered.

## Prerequisites

- **Weeks 5–9 of C30 complete, Week 9 in particular.** This week containerizes the same `notes` service Week 5 started (REST), Week 6 put on Postgres, Week 7 gave a gRPC surface, Week 8 hardened, and Week 9 instrumented. If your Week 9 lab (the instrumented `notes` with `slog`, OTel, and Prometheus metrics) is not green, finish it first — there is nothing meaningful to containerize otherwise.
- **A working `go version` of `1.22` or newer.** This track targets Go 1.22+ for generics, `slog`, and the modern `net/http` routing the whole service assumes.
- **Docker (or Podman) with BuildKit.** Required to build the multi-stage image, to use the cache mounts, and to run the compose stack. BuildKit is the default in Docker 23+; the cache-mount syntax requires it. The daemon must be running before `docker build` or `docker compose up`.
- **`docker compose` v2** (`docker compose version` ≥ 2.x). The compose stack uses the v2 `compose.yaml` schema and the `depends_on: condition: service_healthy` gate.
- **The Week 9 observability config** — the Prometheus scrape config, the Grafana dashboard JSON, and the OTLP exporter endpoint — carried forward; the compose stack wires them to the containerized service.
- **A terminal comfortable with `curl`, `docker images`, and reading a build log.** The container material punishes skimming — a missed `CGO_ENABLED=0` or a `COPY . .` before `go mod download` costs you either a broken binary or a 60-second rebuild — so read the Dockerfile, do not glance at it.

## Topics covered

- **Multi-stage Dockerfiles for Go.** The `golang:1.22` build stage → distroless runtime stage pattern; copying only the binary across the stage boundary; build args (`TARGETOS`, `TARGETARCH`) for cross-compilation; the `-ldflags="-s -w"` strip.
- **Static builds.** `CGO_ENABLED=0`, what it turns off (the C linker, `net` and `os/user` CGO paths), why it is required for `scratch` and recommended for distroless static, and the `-tags netgo,osusergo` belt-and-braces.
- **Distroless and `scratch` base images.** `gcr.io/distroless/static-debian12` (CA certs, tzdata, `nonroot` user, no shell) vs `scratch` (truly empty — you supply CA certs yourself); the no-shell tradeoff; why you observe via logs and traces, not by shelling in.
- **Non-root containers.** `USER nonroot:nonroot` / `USER 65532:65532`; binding a high port; the Kubernetes `securityContext` that enforces it next week (`runAsNonRoot`, `readOnlyRootFilesystem`).
- **Build performance.** The `go.mod`/`go.sum` copy + `go mod download` before the source copy; BuildKit cache mounts for `/go/pkg/mod` and `/root/.cache/go-build`; layer caching; reproducible builds with `-trimpath`.
- **`.dockerignore`.** Keeping `.git/`, `*.env`, `testdata` caches, the compose files, and the README out of the build context.
- **12-factor config.** Config strictly from the environment; the validated config struct loaded once; no secrets in image layers; the same image across environments; logs to stdout; the stateless process; fast startup and clean shutdown (disposability).
- **The local full stack.** A `compose.yaml` bringing up `notesd` + Postgres + Jaeger + Prometheus + Grafana; the `depends_on: service_healthy` gate; the env-var wiring that mirrors the cloud topology.
- **Image measurement.** `docker images`, `docker history`, `dive`; the size table across single-stage, multi-stage `debian`, distroless, and `scratch`, and what each layer is.

## The "it runs in a container" promise

C30 has treated `go vet`, `staticcheck`, and `go test -race` as the clean-build contract for nine weeks. For Week 10 we add a **container contract**: **the same image runs identically in dev, in the compose stack, and (next week) in Kubernetes — because it carries no environment-specific config, no secrets, and no shell.** Concretely — `docker build` produces a sub-15-MB distroless image; `docker run` with the right environment variables starts it; `docker compose up` brings the whole stack online; and the only thing that changes between your laptop and the cluster is the values of a handful of environment variables. An image that must be rebuilt to change a database password, or that bakes a `config.dev.yaml` into a layer, fails this contract.

> **Note on tooling.** Build: Docker Engine 23+ with BuildKit (or `podman`/`buildah`), base images `golang:1.22` for the build stage and `gcr.io/distroless/static-debian12:nonroot` for the runtime stage (`scratch` for the absolute-minimum variant). Compose: `docker compose` v2 with `postgres:16`, `jaegertracing/all-in-one:1.57`, `prom/prometheus:v2.52.0`, and `grafana/grafana:11.0.0`. Image tooling: `docker images`, `docker history`, and optionally `dive` (<https://github.com/wagoodman/dive>) and `docker scout` (<https://docs.docker.com/scout/>) for the CVE-count stretch in challenge-01. Go: the toolchain 1.22.x with `CGO_ENABLED=0`. All free and open source; the whole stack runs on a laptop with no cloud account.
