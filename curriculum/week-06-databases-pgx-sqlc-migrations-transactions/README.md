# Week 6 — Databases: `pgx` Connection Pools, `sqlc` Type-Safe Queries, `golang-migrate`, and Transactions

Welcome to **C30 · Crunch Go**, Week 6. Last week we built the layered `notes-api` with an in-memory repository behind an interface — and we promised that interface was the seam where a real database would slot in. This week we make good on it: we replace `MemRepo` with a Postgres-backed `PgRepo`, and nothing above the repository changes. The handler, the service, the middleware, the tests against a fake repository — all untouched. That is the payoff of last week's seam, and it is the whole reason we drew the boundary where we did. The technology is **Postgres in a container**, the **`pgx`** driver and connection pool (`github.com/jackc/pgx/v5`), **`sqlc`** for compile-time-checked queries generated from hand-written SQL, and **`golang-migrate`** for forward-and-back schema migrations. The question carrying the week: *what SQL does your service actually send, what transaction boundary does each use case need, and what concurrent-write hazard are you exposed to if you get the boundary wrong?*

The first thing to internalize is **why `sqlc`, and not an ORM**. The Go ecosystem has ORMs (GORM is the well-known one), but the senior-Go default for a service that values legible, reviewable SQL is *not* an ORM — it is `sqlc`. You write the SQL by hand in a `.sql` file, annotate each query with a name and a result cardinality, run `sqlc generate`, and get back type-safe Go functions whose parameters and return types match your queries and your schema *exactly*, checked at code-generation time. There is no query DSL to learn, no struct-tag magic, no surprise N+1 from a lazily-loaded association, and no runtime reflection — the generated code is plain Go you can read. The SQL in your repository is the SQL on the wire, with no translation layer guessing. When a query is slow, you `EXPLAIN` the exact statement you wrote. The canonical reference is the `sqlc` documentation at <https://docs.sqlc.dev/>. The trade — you write SQL instead of method chains — is one a Go shop accepts gladly, because the SQL is the part you want to own.

The second thing to internalize is **`pgx` and the connection pool**. `pgx` is the de-facto Postgres driver for Go — it is what `sqlc`'s default Go output targets, and it is faster and more Postgres-native than the older `database/sql` + `lib/pq` path. You almost never open a single connection; you open a `*pgxpool.Pool`, a concurrency-safe pool of connections that hands one out per query and returns it after. The pool has a max size (`pool.Config().MaxConns`); sizing it is a real decision — too small and requests queue waiting for a connection, too large and you exhaust Postgres's `max_connections`. Every query method takes a `context.Context` (Week 4) as its first argument, so a request timeout or a client disconnect cancels the query *on the server* via Postgres's cancellation protocol — the SQL `pg_cancel_backend` happens for you. Citation: the `pgx` docs at <https://pkg.go.dev/github.com/jackc/pgx/v5> and the pool docs at <https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool>.

The third thing to internalize is the **`sqlc` workflow**: schema → queries → generate. You keep your schema in `.sql` files (the same migration files `golang-migrate` applies), you write your queries in a `query.sql` with annotations like `-- name: GetNote :one` (return one row), `:many` (return a slice), or `:exec` (no rows), and `sqlc generate` reads both, type-checks every query against the schema, and emits a `Queries` struct with one Go method per query. A typo in a column name is a *generate-time* error, not a runtime surprise. A query that returns three columns into a struct with two fields fails to generate. This is the "compile-time-checked SQL" promise: the gap between "the SQL is valid against this schema" and "the Go compiles" is closed by `sqlc`. Lecture 1 walks the full schema → query → generate loop with the `notes` table. Citation: <https://docs.sqlc.dev/en/latest/tutorials/getting-started-postgresql.html>.

The fourth thing to internalize is the **migrations workflow with `golang-migrate`**. A migration is a *pair* of SQL files — `000001_create_notes.up.sql` and `000001_create_notes.down.sql` — that move the schema forward (the `up`) and back (the `down`). You apply them with `migrate -path migrations -database "$DATABASE_URL" up`, and you can roll back with `down`. The `up`/`down` discipline is not optional: a migration without a tested `down` is a migration you cannot safely roll back when a deploy goes wrong, and "we cannot roll back" is how a bad migration becomes a 3 AM incident. `golang-migrate` tracks which migrations have run in a `schema_migrations` table, so applying `up` twice is a no-op for already-applied migrations. The rule, which the whole back half of the track depends on: **every migration ships with a `down` that has been run at least once.** Citation: the `golang-migrate` docs at <https://github.com/golang-migrate/migrate>. The mini-project demonstrates a clean `migrate down` and re-`up`.

The fifth thing to internalize is the **transaction and the `BeginTx` pattern**. A transaction groups multiple statements so they either all commit or all roll back — atomicity. In `pgx` you start one with `tx, err := pool.Begin(ctx)`, run statements on `tx`, and end with `tx.Commit(ctx)` or `tx.Rollback(ctx)`. The idiomatic Go shape uses `defer tx.Rollback(ctx)` immediately after `Begin` — a rollback after a successful commit is a harmless no-op, so the `defer` guarantees you never leak an open transaction on an early return or a panic, and the explicit `Commit` at the end is the only thing that persists the work. A transaction boundary should map to *one use case*: "transfer money" is one transaction (debit and credit must both happen or neither), "create a note" is one transaction (even if it touches two tables). Drawing the boundary correctly is the heart of correct data-layer code. Lecture 2 covers the `BeginTx` pattern and the `sqlc`-with-transactions idiom (`q.WithTx(tx)`). Citation: <https://pkg.go.dev/github.com/jackc/pgx/v5#Tx>.

The sixth thing to internalize is **isolation levels and concurrent-write hazards**. Postgres's default isolation level is `READ COMMITTED`, which prevents some anomalies but not others. The two hazards you must be able to reason about: the **lost update** (two transactions read a value, both compute a new one, both write — one update is lost) and **write skew** (two transactions each read a set, each check a constraint that still holds, each write — together violating the constraint). The cures are `SELECT ... FOR UPDATE` (take a row lock so the second reader waits), a higher isolation level (`REPEATABLE READ` or `SERIALIZABLE`, which makes Postgres detect and abort conflicting transactions), or an optimistic-concurrency version column (the `If-Match`/`ETag` pattern from Week 5's stretch goal). You do not need to memorise the SQL standard's anomaly taxonomy, but you must be able to look at a use case and say "this has a lost-update hazard; here is how I close it." Lecture 3 walks both hazards with reproducible SQL and the three cures. Citation: the Postgres transaction-isolation docs at <https://www.postgresql.org/docs/current/transaction-iso.html>.

The seventh thing to internalize is **`context` deadlines on every query**. Every `pgx` and `sqlc` method takes a `ctx` as its first argument, and you pass the request's context (or a tighter `context.WithTimeout`) into it. When that context is cancelled — the client hung up, the request timed out, the server is shutting down — `pgx` sends a cancel request to Postgres, which aborts the running query and returns the connection to the pool. A query with no deadline is a query that can hang a connection (and, transitively, your pool) indefinitely when the database is slow. The discipline from Week 4 and Week 5 — thread `ctx` everywhere — pays off here: a slow query under a 2-second request budget is *cancelled* at 2 seconds instead of holding a pool slot until Postgres finishes. Citation: <https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool#Pool.QueryRow>.

The eighth thing to internalize is **integration testing against a real Postgres**. You cannot test a SQL repository against a fake — the whole point is the SQL, the types, and the transactions, none of which a fake exercises. So the repository's tests run against a *real* Postgres in a container. Two idioms: a `docker compose` harness you bring up before the test run, or `testcontainers-go`, which spins up an ephemeral Postgres container *from within the test*, applies the migrations, runs the tests, and tears it down. The repository tests are the only layer that needs a database (the seam from Week 5 means the service and handler tests use a fake). These integration tests are slower than unit tests — seconds, not microseconds — which is exactly why the testing pyramid (Week 8) puts few of them at the top. Citation: `testcontainers-go` at <https://golang.testcontainers.org/>. Lab 06 writes integration tests against a real Postgres container, including a multi-step transaction and a clean `migrate down` and re-`up`.

The ninth thing to internalize is that **the repository is where `pgx` types stop**. The `PgRepo` implements the same `Repository` interface the service defined (Week 5) — it takes domain types and a `context`, returns domain types and the same sentinel errors (`ErrNotFound`, `ErrConflict`). Inside, it translates: a `sqlc`-generated row struct becomes a domain `Note`; a `pgx.ErrNoRows` becomes `ErrNotFound`; a unique-constraint violation (Postgres error code `23505`) becomes `ErrConflict`, classified with `pgconn.PgError`. The service never sees a `pgx` type or a SQL error code — that mapping is the repository's job, and it is what keeps the service database-agnostic and the seam intact. Lecture 2 covers the error-translation layer. Citation: the `pgconn` error docs at <https://pkg.go.dev/github.com/jackc/pgx/v5/pgconn#PgError>.

By the end of the week you will be the person on your team who can answer "why is this write losing data under load" with the transaction boundary, the isolation level, and the `SELECT ... FOR UPDATE` or version column that closes the hazard — not with "let me add a retry and hope."

## Learning objectives

By the end of this week, you will be able to:

- **Configure** a `*pgxpool.Pool` against Postgres, size `MaxConns` deliberately, and reason about the pool-size-vs-`max_connections` trade-off. Cite <https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool>.
- **Write** SQL queries annotated for `sqlc` (`:one`, `:many`, `:exec`, `:execrows`), run `sqlc generate`, and use the type-safe `Queries` methods. Explain how a column typo becomes a generate-time error. Cite <https://docs.sqlc.dev/>.
- **Defend** the `sqlc`-over-ORM choice for a service that values legible SQL, and name the one case where an ORM's productivity might win.
- **Author** reversible `golang-migrate` migrations as `up`/`down` SQL pairs, apply them with `migrate up`, roll back with `migrate down`, and explain the `schema_migrations` tracking table. Cite <https://github.com/golang-migrate/migrate>.
- **Use** transactions correctly: `pool.Begin(ctx)`, `defer tx.Rollback(ctx)`, an explicit `tx.Commit(ctx)`, and `q.WithTx(tx)` to run `sqlc` queries inside the transaction. Map a transaction boundary to one use case. Cite <https://pkg.go.dev/github.com/jackc/pgx/v5#Tx>.
- **Reason** about concurrent-write hazards — the lost update and write skew — and close each with `SELECT ... FOR UPDATE`, a higher isolation level, or an optimistic version column. Cite <https://www.postgresql.org/docs/current/transaction-iso.html>.
- **Thread** `context` deadlines into every query so a request timeout cancels the query server-side via Postgres's cancellation protocol. Cite the `pgx` query docs.
- **Translate** at the repository boundary: `pgx.ErrNoRows` → `ErrNotFound`, a `23505` unique violation (via `pgconn.PgError`) → `ErrConflict`, a `sqlc` row → a domain type. Keep `pgx` types out of the service. Cite <https://pkg.go.dev/github.com/jackc/pgx/v5/pgconn#PgError>.
- **Write** integration tests against a real Postgres container with `testcontainers-go` (or a compose harness): apply migrations, run the tests, tear down. Test a multi-step transaction and a `migrate down`/re-`up`. Cite <https://golang.testcontainers.org/>.
- **Cite** the `pgx`, `pgxpool`, and `pgconn` package docs, the `sqlc` documentation, the `golang-migrate` docs, and the Postgres transaction-isolation manual for every technique covered.

## Topics covered

- **`pgx` and the pool.** `pgxpool.New`, `pool.Acquire`/`Release`, `MaxConns`/`MinConns`, `QueryRow`/`Query`/`Exec`, the `context`-cancellation-to-Postgres path, the difference from `database/sql` + `lib/pq`.
- **`sqlc`.** The `sqlc.yaml` config, the schema input, the annotated `query.sql` (`:one`/`:many`/`:exec`/`:execrows`/`:batchexec`), `sqlc generate`, the generated `Queries`/`Querier` types, the `pgx/v5` Go output, embedded structs vs scalar returns.
- **Migrations.** `golang-migrate`, the `up`/`down` file pair, `migrate create`/`up`/`down`/`goto`/`force`, the `schema_migrations` table, the "every migration has a tested down" rule, applying migrations in tests, the production split (script vs auto-apply).
- **Transactions.** `pool.Begin`/`tx.Commit`/`tx.Rollback`, the `defer tx.Rollback(ctx)` idiom, `q.WithTx(tx)`, mapping a boundary to a use case, savepoints (named, not deep), `pgx.BeginTxFunc`-style helpers.
- **Isolation and hazards.** `READ COMMITTED` (default), `REPEATABLE READ`, `SERIALIZABLE`; the lost update; write skew; `SELECT ... FOR UPDATE`; serialization-failure retries (`40001`); the optimistic version-column pattern.
- **Context on queries.** Threading the request context, server-side cancellation, query timeouts, the consequence of a deadline-less query.
- **Error translation at the repository.** `pgx.ErrNoRows` → `ErrNotFound`; `pgconn.PgError` codes (`23505` unique, `23503` foreign key, `40001` serialization failure) → domain errors; keeping `pgx` out of the service.
- **Integration testing.** `testcontainers-go` (ephemeral Postgres from the test), a `docker compose` harness, applying migrations before tests, table-driven repository tests, the transaction test, the `migrate down`/re-`up` test, why these belong at the top of the pyramid.
- **The worked example: `notes-api` on Postgres.** Last week's `notes-api`, with `MemRepo` replaced by a `sqlc`+`pgx` `PgRepo`, reversible migrations, a multi-step transaction (a note plus an audit row in one commit), and integration tests against a real Postgres container. ## The "go vet clean" promise — restated, and a new migration promise

C30 treats a clean toolchain run as a contract:

```
$ sqlc generate && go vet ./... && staticcheck ./... && go test ./...
ok  	github.com/you/notes-api	2.114s
```

For Week 6 we add a migration contract: **every migration ships as an `up`/`down` pair, and you have run the `down` at least once.** A migration without a tested `down` is a migration you cannot roll back, and "we cannot roll back" is how a bad deploy becomes an incident. The mini-project requires you to demonstrate a clean `migrate down` and re-`up`; that demonstration *is* the test of your `down`.

We add a SQL-on-the-wire contract too: **the SQL `sqlc` generates is the SQL you wrote, and you can produce the exact statement for any query in your service.** A query whose generated SQL nobody has read is a query that has not been reviewed — the same wire-bytes discipline Week 4 applied to the race detector and Week 5 to status codes, now applied to SQL. `sqlc generate` shows you the SQL; `EXPLAIN` shows you the plan; there is no translation layer hiding either.

> **Note on packages.** The driver and pool are `github.com/jackc/pgx/v5` and `.../pgx/v5/pgxpool` (MIT). Error codes come from `.../pgx/v5/pgconn`. Queries are generated by `sqlc` (the `sqlc` binary; the generated code imports only `pgx`). Migrations are `golang-migrate` (the `migrate` binary; the migrations themselves are plain `.sql`). Integration tests use `github.com/testcontainers/testcontainers-go` and its `postgres` module (MIT). Postgres runs in Docker. All free, all open source.
